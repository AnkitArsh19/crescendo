# Workflow Runs & Diagnostic Logs

Every time an active workflow triggers, Crescendo instantiates an individual execution record called a **Workflow Run**. The Runs console provides granular step-by-step diagnostic telemetry, making it simple to monitor operational reliability and troubleshoot integration errors.

## Understanding Run Statuses

When navigating to **Workflow Runs** under your workspace monitor, executions are organized chronologically and categorized by runtime state:
* **PENDING:** The triggering event has been ingested into the distributed messaging queue and is awaiting background worker thread pool assignment.
* **RUNNING:** An active virtual worker thread is progressively processing step action nodes and executing external network requests.
* **SUCCESS:** Every sequential node and conditional branch within the graph executed cleanly without unhandled provider exceptions.
* **FAILED:** An integration step encountered a fatal network timeout, authentication error, or invalid data payload formatting that prevented further execution.
* **CANCELLED:** An active long-running workflow instance was manually terminated by a workspace administrator prior to completion.

## Step-by-Step Execution Logs

Clicking any specific Run ID entry opens the **Execution Detail Modal**, displaying an exact transcript of events across the workflow lifecycle.

### Diagnostic Telemetry Information
For every evaluated node step, the log captures critical troubleshooting data:
* **Execution Latency (ms):** The exact elapsed runtime consumed by external API responses or local logical calculations.
* **Input Payload Configuration:** The exact evaluated JSON arguments submitted to the third-party application handler after dynamic variable interpolation resolves.
* **Provider Output Response:** The raw HTTP status code, response headers, and structured JSON return payloads generated by external integration endpoints (e.g., Jira ticket IDs or Slack message timestamps).
* **Stack Trace Error Details:** Direct feedback text returned by external REST endpoints during failure conditions (e.g., `401 Unauthorized: Invalid or expired Slack OAuth access token`).

## Replaying & Retrying Failed Executions

When an automated sequence halts due to external service outages, network disruptions, or expired credentials, Crescendo enables non-destructive diagnostic replaying.

### Automatic Retry Retry Policies
By default, standard integration actions feature built-in exponential backoff retry algorithms. If a transient error occurs (such as an external SaaS server returning a `503 Service Unavailable` or `429 Too Many Requests` status code), the background worker automatically schedules up to three progressive retry execution attempts before declaring the Run status as `FAILED`.

### Manual Diagnostic Replay
If a workflow run fails due to configuration errors or expired OAuth tokens, you can resolve the underlying issue and trigger an instant replay without re-sending external webhook ingestion traffic:
1. Navigate to the failed run entry inside **Workflow Runs** and review the failing node error details.
2. If necessary, open the **Connections** tab in a separate browser window to re-authenticate expired account credentials, or update target field mappings inside the workflow canvas.
3. Return to the failed Run Detail Modal and click **Replay Run**.
4. The execution engine instantiates a clean execution instance utilizing the exact original stored ingestion trigger parameters, resuming downstream integration tasks from the corrected starting state.
